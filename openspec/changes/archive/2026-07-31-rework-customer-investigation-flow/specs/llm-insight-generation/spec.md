## MODIFIED Requirements

### Requirement: LLM insight generation from Neo4j evidence
The system MUST generate structured insights by sending enriched Neo4j evidence for a customer to an LLM (or a deterministic static adapter) after graph retrieval and before final response assembly.

#### Scenario: Insights are generated from retrieved evidence
- **WHEN** the workflow has collected evidence items for a customer
- **THEN** it SHALL build an insight request using the customer id, any pre-existing alert context, and the evidence payload
- **AND THEN** it SHALL store generated insights in workflow state for downstream response composition

#### Scenario: Insight generation handles no-evidence cases
- **WHEN** the workflow has no related evidence for the customer
- **THEN** it SHALL send a constrained context indicating no related evidence
- **AND THEN** it SHALL produce a safe default insight message without failing the workflow

### Requirement: Insight output remains structured
The system MUST normalize insight output into a predictable structure for consumers, including whether an alert is recommended.

#### Scenario: Insight response is normalized
- **WHEN** an insight adapter returns content for a customer
- **THEN** the workflow SHALL map the result into predefined fields for summary, key observations, and alert recommendation
- **AND THEN** the final response SHALL include those fields even when some values are empty

#### Scenario: LLM failure does not break triage completion
- **WHEN** an LLM call fails due to timeout, provider error, or invalid response
- **THEN** the workflow SHALL record an insights error status
- **AND THEN** it SHALL continue to produce a completed triage result with fallback insight content and no alert recommendation

## ADDED Requirements

### Requirement: Static/real-LLM selection via a single environment toggle
The system MUST let an operator choose between deterministic static insights and a real LLM call using one environment variable, without requiring code changes.

#### Scenario: LLM is disabled
- **WHEN** `AML_ALERT_LLM_ENABLED` is `false`
- **THEN** the system SHALL generate insights using the deterministic rule-based adapter, producing evidence-grounded text without any network call

#### Scenario: LLM is enabled
- **WHEN** `AML_ALERT_LLM_ENABLED` is `true`
- **THEN** the system SHALL generate insights using a real LLM provider selected by `AML_ALERT_LLM_PROVIDER`

### Requirement: LLM provider selection via environment configuration
The system MUST support selecting between the Anthropic Claude API and the OpenAI API as the real-LLM provider via `AML_ALERT_LLM_PROVIDER`, without any code change.

#### Scenario: Anthropic provider is selected
- **WHEN** `AML_ALERT_LLM_ENABLED` is `true` and `AML_ALERT_LLM_PROVIDER` is `anthropic`
- **THEN** the workflow SHALL send the composed insight prompt to the Anthropic Claude API and map the structured response into the normalized insight fields

#### Scenario: OpenAI provider is selected
- **WHEN** `AML_ALERT_LLM_ENABLED` is `true` and `AML_ALERT_LLM_PROVIDER` is `openai`
- **THEN** the workflow SHALL send the composed insight prompt to the OpenAI Chat Completions API and map the structured JSON response into the normalized insight fields

#### Scenario: Default model and reasoning effort are applied when unset
- **WHEN** the `openai` provider is selected and no explicit model or reasoning effort override is configured
- **THEN** the system SHALL use the default OpenAI model and request `medium` reasoning effort
- **AND THEN** an explicitly configured model or reasoning effort value SHALL override its respective default

#### Scenario: Model is selected via environment configuration alone
- **WHEN** an operator sets `AML_ALERT_LLM_MODEL` to a specific model name (e.g. a Claude model when `AML_ALERT_LLM_PROVIDER=anthropic`, or a GPT model when `AML_ALERT_LLM_PROVIDER=openai`)
- **THEN** the system SHALL use that exact model for the selected provider's requests
- **AND THEN** switching models or providers SHALL require only `.env` changes, with no code change

### Requirement: Evidence-grounded alert recommendation
The system MUST derive an alert recommendation from the supplied evidence, whether generated deterministically (static mode) or by a real LLM, and MUST NOT recommend an alert without evidence support.

#### Scenario: Static mode mirrors structural risk signals
- **WHEN** insights are generated in static (rule-based) mode
- **THEN** the alert recommendation SHALL be true only when the evidence includes a detected cycle or structuring fan-out/fan-in pattern

#### Scenario: Real LLM mode is instructed to stay grounded
- **WHEN** insights are generated by a real LLM provider
- **THEN** the request SHALL instruct the model to recommend an alert only when the supplied evidence shows a concrete suspicious pattern, never from absence of evidence or speculation

#### Scenario: Real LLM provider failures fall back like other failures
- **WHEN** the `openai` or `anthropic` provider call fails due to timeout, provider error, or invalid response
- **THEN** the workflow SHALL record an insights error status and continue to produce a completed triage result with fallback insight content, consistent with existing provider failure handling
