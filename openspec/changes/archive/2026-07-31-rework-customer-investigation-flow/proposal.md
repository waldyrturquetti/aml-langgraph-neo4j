## Why

The workflow currently investigates a pre-defined fictional `Alert` payload picked by `--alert-id` from a hardcoded Python dict (`SAMPLE_ALERTS`); the `Alert` nodes seeded into Neo4j are purely cosmetic and are never queried by the application. This inverts the intended AML use case, where an analyst investigates a *customer* and the system determines whether an alert is warranted. The project owner wants the graph and workflow reoriented around customers/accounts/transactions as the source of truth, with alerts as a *discovered* artifact the workflow writes back to Neo4j when the evidence (interpreted by an LLM, or deterministically in static mode) warrants it. This proposal also folds in the previously-scoped OpenAI provider addition, since both land in the same insight-generation code path.

## What Changes

- **Investigation entry point becomes `--customer-id`** instead of `--alert-id`. The CLI, `TriageState`, and `InsightRequest` are restructured around a `customer_id` rather than an `AlertPayload`. **BREAKING**: `--alert-id` is removed; `SAMPLE_ALERTS` is removed.
- **Seed dataset is regenerated to 50 customers**: 30 with ordinary organic activity, 20 with an injected suspicious pattern (directed transfer cycle, or structuring fan-out/fan-in). Only 2 of the 20 suspicious customers get a pre-existing `Alert` node in the seed data; the other 18 are undiscovered until investigated. The generator becomes a versioned, deterministic script (`scripts/generate_dataset.py`) that produces both `src/aml_alert_triage/graph_dataset.py` and `data/neo4j/seed.cypher`.
- **The workflow writes `Alert` nodes back to Neo4j.** After insight generation, if the insight response recommends an alert and the customer does not already have one, the workflow creates an `Alert` node and a `TARGETS` relationship. If an alert already exists for that customer, no duplicate is created — the workflow reports the existing one instead.
- **The insight response gains a `recommend_alert` (+ reason) field**, produced by every provider (rule-based and real LLM). In real-LLM mode this is the model's own grounded judgment; in static/rule-based mode it mirrors the same structural signal `assess_risk` already uses (cycle/structuring detected), so the two modes stay behaviorally consistent when nothing is ambiguous.
- **`AML_ALERT_LLM_ENABLED` becomes the single static/LLM toggle**: `false` now routes to the deterministic rule-based adapter (evidence-grounded static text) instead of the current disabled/generic-fallback adapter; `true` routes to a real LLM chosen by `AML_ALERT_LLM_PROVIDER`. `DisabledLLMAdapter` is removed as dead code.
- **Add an `openai` LLM provider** alongside the existing `anthropic` provider, selectable via `AML_ALERT_LLM_PROVIDER=openai|anthropic` in `.env`, following the same adapter pattern, with an optional reasoning ("thinking") mode defaulted to `medium` for reasoning-capable models.
- **Detect association with already-alerted customers.** A new targeted query flags a customer who is connected — even indirectly, up to a configurable hop ceiling (`AML_ALERT_PROXIMITY_MAX_HOPS`) — to another customer who already has an `Alert`. This `alert-proximity` evidence is treated as high risk, the same severity as a detected cycle or structuring pattern, and is one of the factors feeding the alert-recommendation decision.
- **Generalize evidence retrieval to a real, configurable N-hop traversal.** `NEO4J_MAX_HOPS` currently only has an effect at 1 or 2 hops (the 2-hop query is a one-off hardcoded pivot join); it becomes a genuine ceiling on how many hops the evidence-widening search can traverse before insights are generated, implemented as an iterative hop-by-hop frontier expansion (both in the live Cypher path and the offline `graph_engine.py` mirror).
- **Add a Markdown investigation report, generated on demand from an alert id.** When `register_alert` creates a new alert, it also persists an immutable snapshot of the evidence, risk assessment, and insight (static or LLM, whichever produced that alert) to a DynamoDB table — not the live Neo4j graph, since the report must reflect "why this was flagged" at flagging time even if the graph changes later. A new `--report-alert-id` CLI command reads that snapshot and renders a `.md` file (default `reports/<alert_id>.md`) explaining why the case is suspicious, plus the related people/accounts and transactions that produced the alert. DynamoDB Local and `dynamodb-admin` (for browsing the table) are added to `docker-compose.yml`. The 2 pre-registered alerts get seeded snapshots too, via a new `--seed-dynamodb` CLI step and generator output.
- Update README and `.env.example` to reflect the new CLI flags, dataset composition, alert write-back behavior, both LLM providers, and the new DynamoDB service.

## Capabilities

### New Capabilities
- `alert-report-generation`: persist an immutable per-alert evidence/insight snapshot at creation time and render it on demand as a Markdown investigation report.

### Modified Capabilities
- `aml-alert-triage`: investigation now starts from a customer id rather than a fictional alert payload; evidence enrichment also looks up any pre-existing alert for the customer; the seed dataset composition requirement is updated to 50 customers (30 organic / 20 suspicious, 2 pre-registered alerts); a new requirement covers idempotent alert write-back to Neo4j.
- `llm-insight-generation`: insight responses gain an alert recommendation field across all providers; the `openai` provider is added; provider/enabled-flag semantics are clarified so `AML_ALERT_LLM_ENABLED` alone switches between static and real-LLM insight generation.

## Impact

Affected areas: `src/aml_alert_triage/models.py` (state/record shape), `src/aml_alert_triage/workflow.py` (new `register_alert` step, customer-id-based initialization), `src/aml_alert_triage/repository.py` (alert lookup/creation queries), `src/aml_alert_triage/llm.py` (schema change, `openai` adapter, toggle fix), `src/aml_alert_triage/config.py` (reasoning-effort field, DynamoDB settings), `src/aml_alert_triage/main.py` (new CLI flags), `src/aml_alert_triage/graph_dataset.py` and `data/neo4j/seed.cypher` (regenerated dataset + alert seeds), new `scripts/generate_dataset.py`, new `src/aml_alert_triage/snapshot_store.py` and `src/aml_alert_triage/report.py`, new `data/dynamodb/seed.json`, `docker-compose.yml` (DynamoDB Local + dynamodb-admin services), `pyproject.toml` (`openai` and `boto3` dependencies), `tests/*` (updated fixtures and new coverage), `README.md` and `.env.example`. `sample_data.py` and `SAMPLE_ALERTS` are removed.
